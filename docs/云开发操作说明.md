# 操作指南

这份说明用于维护已迁移到微信云开发的菜谱、轮播图、图片和抖音视频链接。

## 一、需要编辑的文件

日后切换云环境时，只需编辑：

`config/cloud.js`

将下列占位值替换为微信云开发控制台中的环境 ID：

```js
const CLOUD_ENV_ID = 'YOUR_CLOUD_ENV_ID'
```

菜谱已从前端代码中移除，后续新增和修改都在云数据库的 `recipes` 集合中完成。

## 二、当前数据位置

`recipes` 集合是菜谱的唯一数据来源。前端通过 `utils/data.js` 从该集合读取数据；搜索页为了减少请求会保留最长一分钟缓存，其余页面重新进入后会读取最新云端数据。

原始迁移备份位于 `migration/recipes.cloud-import.json`，仅用于备份或重新初始化数据库，不会被打包进小程序。

## 三、维护菜谱数据

1. 打开“云开发”并进入“数据库”。
2. 打开 `recipes` 集合，新增或编辑对应菜谱文档。
3. 保持现有字段结构不变，尤其是 `id`、`title`、`category`、`ingredients`、`steps`、`douyinVideos`。
4. 新菜谱请使用未占用的数字 `id`，并将 `_id` 设置为 `recipe-<id>`。
5. 修改完成后在真机预览中抽查首页、分类、搜索和详情页。

建议为 `id`、`category`、`cuisine`、`featured`、`likes` 创建索引，以便后续按菜谱、分类和热度查询。

## 四、维护首页轮播图

轮播图由 `banners` 集合管理，前端不再保留轮播文案。

1. 在云数据库中新建集合 `banners`。
2. 使用控制台的“导入”功能，导入 `migration/banners.cloud-import.json`；首次导入选 **Insert（插入）**。
3. 每条轮播图包含以下字段：

```json
{
  "_id": "banner-family-dinner",
  "title": "给家人做一顿热饭",
  "page": "cn",
  "sort": 10,
  "enabled": true,
  "imageFileId": ""
}
```

4. `title` 是轮播文案；`page` 是点击后进入的菜谱分类 key；`sort` 数字越小越靠前；`enabled` 为 `false` 时隐藏该轮播图。未填写 `enabled` 时默认显示。
5. 图片可二选一：填写云存储完整 `cloud://...` fileID 到 `imageFileId`，或填写可直接访问的 HTTPS 图床链接到 `imageUrl`。不要保存会过期的云存储临时 HTTPS 地址；未填写时，前端会显示保留的中性占位图。
6. 前端会自行排序，因此 `banners` 集合无需为轮播图读取额外建立索引。

## 五、图片上传与绑定（管理员手动维护官方菜谱）

每条菜谱可使用云存储 fileID 或 HTTPS 图床链接：

```json
{
  "coverImageFileId": "",
  "stepImageFileIds": [],
  "coverImageUrl": "",
  "stepImageUrls": []
}
```

1. 使用云存储时，将封面 fileID 写入 `coverImageFileId`，将步骤图 fileID 按顺序写入 `stepImageFileIds`。
2. 使用图床/CDN 时，将封面 HTTPS 直链写入 `coverImageUrl`，将步骤图 HTTPS 直链按顺序写入 `stepImageUrls`。
3. 图床链接必须为 HTTPS、可直接返回图片文件、没有登录页或防盗链跳转。
4. 在小程序管理后台的“开发管理 → 开发设置 → 服务器域名”中，将图床/CDN域名加入下载文件合法域名；发布版不能依赖开发者工具的“不校验合法域名”选项。

> 用户在小程序内自己发布菜谱时的封面图上传（发布页 → 云存储 → `resolveImage` 云函数换地址）见第十三节，字段格式与这里一致，两者共用同一套读取逻辑。

## 六、补充抖音视频链接

每条菜谱都已包含 `douyinVideos` 字段。已有 33 道精选菜谱保留了 99 个已存在的链接，其余菜谱暂时为空数组。

在抖音中搜索菜名和“做法”，确认视频内容与菜谱相符后，使用“分享 → 复制链接”，并将内容加入对应菜谱：

```json
{
  "douyinVideos": [
    {
      "title": "菜名家常做法",
      "url": "https://www.iesdouyin.com/share/video/<视频 ID>"
    }
  ]
}
```

一条菜谱可添加多个链接。请只保存经核验的分享链接，不要猜测链接、下载或重新托管第三方视频。

## 七、前端读取机制

小程序已通过 `utils/data.js` 读取 `recipes` 与 `banners` 集合。本地菜谱、视频映射和轮播文案已移除，不再需要随小程序版本更新。

常规内容维护只需要在云开发控制台修改数据库；无需改动前端代码或重新发布小程序。

## 八、上线前检查

1. `config/cloud.js` 已填写正确环境 ID。
2. `recipes` 集合中有 xxx 条菜谱。
3. 至少抽查封面、步骤图和抖音链接是否对应正确菜谱。
4. 数据库权限已配置为：`recipes`、`comments` 所有用户可读，仅创建者可写（用于支持用户自创菜谱与评论，见第十节）；云存储权限维持默认（普通用户可读）。
5. `login` 云函数已重新部署（见第十四节），登录后自动出现 `ai_conversations`、`favorites`、`feedback` 三个“仅创建者可读写”的个人集合。
6. 使用真机预览，确认图片临时链接、列表加载和详情页视频复制功能正常。

## 九、数据库性能优化（必须完成）

分类页和首页会按分类筛选、按热度排序、按菜系计数。请在云开发控制台 → 数据库 → `recipes` 集合 → 索引管理中创建以下索引：

| 索引字段 | 顺序 | 用途 |
| --- | --- | --- |
| `id` | 升序，唯一 | 按菜谱 ID 打开详情、收藏和浏览历史 |
| `featured` | 升序 | 首页今日推荐、热门搜索词 |
| `likes` | 降序 | 首页热门菜谱 |
| `category` + `likes` | 升序 + 降序 | 分类页只取热度最高的 8 条预览 |
| `category` + `cuisine` | 升序 + 升序 | 菜系列表，以及聚合不可用时的菜系统计兜底 |

创建步骤：

1. 打开 `recipes` 集合，进入“索引管理”。
2. 点击“新建索引”，按上表依次添加字段和排序方向。
3. `id` 索引勾选“唯一”；其余索引不勾选唯一。
4. 等待全部索引状态变为“可用”后，再用真机重新编译测试。

分类页已增加五分钟内存缓存：中式菜系首次进入使用一次聚合统计，其他分类只读取总数和最多 8 条预览；切回已访问过的分类不再重复请求。首页常用数据缓存一分钟，且会保存十分钟首页摘要，后续冷启动可先显示缓存内容再静默刷新。数据库内容改动后，等待对应缓存时间或重新进入小程序即可看到更新。



1. **小程序客户端查询单次最多只返回 20 条**（这是官方限制，云函数端才是 100/1000 条，`utils/data.js` 之前的写法就是因为这个限制才需要分页）。分类数据量大于 20 条时，原来是“先取一页 → 再单独查一次总数 → 其余分页并发请求”，前两步是串行的；详情页里“查菜谱”和“查评论”也是完全串行的两次请求。现在把菜谱和评论改成并发请求（`Promise.allSettled`），减少了详情页的串行往返次数。
2. **图片临时地址经云函数中转会有云函数冷启动开销**：第十三节的方案 B 把图片地址解析从客户端直连云存储改成了走 `resolveImage` 云函数，多了一次云函数调用，而云函数在长时间没有被调用后第一次冷启动通常要多花几百毫秒到一两秒，这也是"不同手机/不同时刻差异较大"的主要来源之一（冷启动发生在服务端，和手机本身关系不大，但恰好解释了"时快时慢"）。为此把封面图地址的本地缓存有效期从 1 分钟延长到 30 分钟（云函数换取地址时也显式声明 2 小时有效期，两边匹配，不会出现缓存过期后地址仍失效的情况），同一批图片在这段时间内重复浏览完全不用再调云函数。
3. 另外给列表类页面（分类列表、我的菜谱、收藏夹、浏览历史）的图片加上了 `lazy-load`，减少一次性解码大量图片的压力——这部分和手机性能直接相关，机型越弱、图片越多，越能感觉到差异，加上懒加载后会明显缓解。


## 十、用户自创菜谱与评论（对所有用户可见）

自 v1.1 起，“自创菜谱”和“评论”不再存于用户本机（`wx.setStorageSync`），而是写入云数据库，因此对所有用户可见，不再局限于发布者本人或本设备。涉及两个集合：

- `recipes`：自创菜谱与官方菜谱共用同一集合（写入时打上 `source: 'user'`），因此会自动出现在首页、分类、搜索、热门等所有已有查询里，无需改动读取逻辑。
- `comments`（新集合）：每条评论一个文档，包含 `recipeId`、`content`、`author`、`createdAt`。评论区不保存头像——`chooseAvatar` 拿到的多是本机临时文件路径，写入数据库后对其他用户/其他设备都是失效链接，因此只展示昵称；用户可以删除自己发表的评论（依据 `_openid` 校验，越权删除会被数据库权限拒绝）。

这两处**只涉及云数据库权限，与云存储无关**——评论和自创菜谱目前都是纯文本，没有上传图片，因此不受“云存储所有用户可读”功能不可用的套餐限制影响。

### 需要在控制台完成的配置

1. 打开云开发控制台 → 数据库 → `recipes` 集合 → 权限设置，将写权限从当前的“仅创建者可写”/自定义规则改为预设的 **“所有用户可读，仅创建者可写”**。
   - 效果：任何登录用户都能新增文档、并删改自己创建的文档（依据系统自动记录的 `_openid`）；无法修改他人创建的文档，官方导入的菜谱因为不属于任何用户的 `_openid`，同样不会被误改。
2. 新建集合 `comments`，权限同样设为 **“所有用户可读，仅创建者可写”**。
3. 进入 `comments` 集合的“索引管理”，新建索引 `recipeId`（升序）+ `createdAt`（降序），用于按菜谱查询评论并按时间倒序展示。
4. 用真机预览验证：发布一道自创菜谱后，换一个账号也能在首页/分类/搜索里看到它；在详情页发表评论后，换一个账号打开同一道菜也能看到该评论。

不需要新增云函数：`recipes` 与 `comments` 的读写都通过小程序客户端 SDK 直接完成，云数据库的权限规则本身就是安全边界（用户只能改自己创建的文档）。如果之后想加内容审核（如发布前人工审核、敏感词过滤），可以再引入一个云函数把直接写库改成“提交云函数 → 云函数校验后代写”，但目前的需求（“对所有用户可见”）不需要这一步。

## 十一、AI 美食助手接入 DeepSeek

`cloudfunctions/aiAssistant` 已经改为对接 DeepSeek 的 Chat Completions 接口（`https://api.deepseek.com/chat/completions`，与 OpenAI 请求格式兼容），代码无需再改，只需要在控制台完成配置并重新部署。

### 需要在控制台完成的配置

1. 在 [DeepSeek 开放平台](https://platform.deepseek.com) 申请 API Key。
2. 打开云开发控制台 → 云函数 → `aiAssistant` → 配置 → 环境变量，新增：

   | 变量名 | 值 | 说明 |
   | --- | --- | --- |
   | `AI_API_KEY` | 你的 DeepSeek API Key | 必填，密钥只存在于云函数端，前端和代码库都不会出现明文 |
   | `AI_MODEL` | `deepseek-v4-flash`（默认）或 `deepseek-v4-pro` | 选填；flash 更省成本，pro 能力更强、价格更高 |
   | `AI_API_URL` | 一般不用填 | 仅在你要接入自建代理/网关时才需要覆盖默认地址 |

3. 在微信开发者工具中右键 `cloudfunctions/aiAssistant` → “上传并部署”，让新代码和环境变量生效（改代码或改环境变量都需要重新部署一次）。
4. 用真机预览打开「AI 美食助手」页面提问，确认能收到回复；若提示“AI 服务未配置”，说明环境变量未生效或部署未成功。

### 涉及的依赖

- **Cloud Functions（必须）**：`aiAssistant` 云函数环境变量 `AI_API_KEY`（必填）、`AI_MODEL`（选填）。
- **Cloud Database（选填）**：`ai_usage` 集合，仅用于限流，不配置也能正常问答。
- **Cloud Storage**：不涉及，AI 问答只处理文本。


## 十二、意见反馈存储在哪里

改为写入云数据库的 `feedback` 集合（`content`、`createdAt`，以及系统自动记录的 `_openid`）。

`feedback` 集合无需手动新建：用户登录时 `login` 云函数会自动创建（见第十四节），新建集合的默认权限即为“仅创建者可读写”。若环境中已提前手动建好，请确认权限为 **“仅创建者可读写”**：

1. 这样每个用户只能通过小程序读到自己提交的记录，看不到别人的反馈。
2. 查看全部反馈：直接在云开发控制台的数据库管理界面打开 `feedback` 集合即可看到所有用户的记录——控制台拥有全部数据的读取权限，不受上面那条“仅创建者可读写”的限制（该权限只约束小程序客户端发起的请求）。

## 十三、自创菜谱封面图（已接入云函数中转，不依赖云存储的“所有用户可读”）

发布页已支持上传封面图，采用方案 B：真正上传到云存储，但图片的读取地址统一由云函数换取，不依赖你目前缺失的“云存储所有用户可读”权限。

**实现方式**
- 上传：发布页调用 `wx.chooseMedia` 选图（自动压缩）+ `wx.cloud.uploadFile` 直接上传到云存储，文件路径为 `recipe-covers/时间戳-随机串.扩展名`；上传得到的 `cloud://` fileID 存入菜谱文档的 `coverImageFileId` 字段。上传本身不受限——任何用户上传自己的文件都没有障碍。
- 读取：新增了云函数 `resolveImage`，内部用服务端 SDK 的 `cloud.getTempFileURL()` 换取临时地址再返回给客户端。`utils/data.js` 的 `resolveFileUrls()`（首页、分类、列表、详情、收藏、我的菜谱、浏览历史等所有需要显示封面图的地方都会经过这一个函数）已经统一改为调用这个云函数，而不是在客户端直接调用 `wx.cloud.getTempFileURL`。
  - 官方文档明确说明：云函数和云开发控制台属于“管理端”，拥有云存储与数据库的完全读写权限，不受控制台里配置的安全规则/权限预设限制——那些权限设置只对小程序客户端发起的请求生效。所以不管文件是官方录入的还是某个用户上传的，`resolveImage` 都能正常换到地址，等效于拥有了“所有用户可读”，但完全不需要那个被套餐禁用的权限开关。
  - 附带的好处：现在云存储的读权限具体设成什么都不再影响图片显示（因为客户端不再直接读云存储了），少了一处需要在控制台操心的配置。
- 移除/替换封面图时会调用 `wx.cloud.deleteFile` 清理旧文件，避免云存储里堆积没用到的图片。
- 封面图是选填项，不影响不上传图片的老发布流程。

**需要在控制台完成的配置**

1. 在微信开发者工具中右键 `cloudfunctions/resolveImage` → “上传并部署：云端安装依赖”。
2. 无需额外的数据库或存储权限配置——`resolveImage` 使用管理端权限，云存储保持默认设置即可。
3. 真机预览验证：在发布页上传一张封面图并发布，换一个账号也能在首页/分类/列表看到这张封面图。

**如果以后还想给制作步骤加图片**：`utils/data.js` 的 `attachDetailImageUrls()` 已经支持 `stepImageFileIds`/`step.imageUrl` 字段和多图解析，读取链路无需改动；只需要在发布页的步骤编辑区，给每一行加上和封面图一样的 `chooseMedia + uploadFile` 交互即可，是同一套机制的重复使用。

## 十四、个人数据集合（AI 聊天记录 / 收藏 / 反馈）——必须重新部署 login 云函数

AI 聊天记录、菜谱收藏、意见反馈都属于“仅本人可见”的个人数据，分别存放在 `ai_conversations`、`favorites`、`feedback` 三个集合中。小程序客户端 SDK **没有创建集合的权限**，集合不存在时读写都会报 `errCode: -502005 database collection not exists`（“我的”页曾因此整体提示“数据加载失败”）。现在 `login` 云函数会在用户每次登录时以管理端身份**幂等创建**这三个集合（已存在则跳过），因此升级后只需重新部署一次云函数。

### 需要在控制台完成的配置（按顺序）

1. 在微信开发者工具左侧资源管理器中右键 `cloudfunctions/login` 文件夹 → **“上传并部署：云端安装依赖（不上传 node_modules）”**，等待部署完成。
2. 重新编译小程序并**退出登录后重新登录一次**（或新用户首次登录），登录成功后到云开发控制台 → 数据库中确认已自动出现 `ai_conversations`、`favorites`、`feedback` 三个集合。
3. 逐个打开这三个集合 → 权限设置，确认均为预设的 **“仅创建者可读写”**（云函数自动创建时就是该默认值，核对一遍即可）：

   | 集合 | 权限 | 用途 |
   | --- | --- | --- |
   | `ai_conversations` | 仅创建者可读写 | 每段 AI 对话一个文档（`messages`、`startedAt`、`updatedAt`），“我的 → 聊天记录”读取 |
   | `favorites` | 仅创建者可读写 | 每条收藏一个文档（`recipeId`、`createdAt`），收藏随账号走、跨设备同步 |
   | `feedback` | 仅创建者可读写 | 意见反馈，开发者在控制台可查看全部 |

4. 建议创建以下索引：
   - `ai_conversations`：`updatedAt` 降序，用于聊天记录按最近更新排序。
   - `favorites`：`recipeId` 升序 + `createdAt` 降序，用于取消收藏查重和按收藏时间排序列表。
5. 真机验证：

### 说明与兜底

- **收藏已整体迁移到云端**：详情页点亮爱心、收藏夹列表、“我的”页收藏数全部读写 `favorites` 集合，不再使用本机缓存；未登录时点收藏会弹窗引导登录，登录后自动完成这次收藏。
